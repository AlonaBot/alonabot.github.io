## 启动的顺序

Core 启动一个插件时依次做这些事。任何一步失败，插件都不会开始接收消息。

| 步骤 | 做什么 | 你的代码 |
| --- | --- | --- |
| 1 | 启动插件进程，建立连接 | `New()` 被调用 |
| 2 | 加载配置，补上缺省值 | `OnConfigLoad` |
| 3 | 执行还没执行过的建表步骤 | `Migrations` 里的函数 |
| 4 | 执行启动回调 | `OnStart` |
| 5 | 插件告诉 Core 自己登记了哪些命令，Core 检查有没有冲突 | |
| 6 | Core 确认这个版本可用，记录下来 | |
| 7 | 即将开始接收消息 | `OnReady` |
| 8 | 开始接收消息 | Handler |

第 6 步是分界线：

- **之前失败**：这次启动不算数。如果是更新，继续用旧版本和旧数据。
- **之后失败**：这个版本已经生效。Core 会尝试重启它。

所以检查配置、连接外部服务这类「可能不成功」的事应该放在 `OnStart` 里，失败时用户还能留在旧版本上。

## 停止的顺序

| 步骤 | 做什么 |
| --- | --- |
| 1 | Core 不再把新消息交给这个插件 |
| 2 | 等正在执行的 Handler 结束，最多几秒 |
| 3 | 执行 `OnStop` |
| 4 | 插件进程退出 |

整个过程有时间上限（缺省 10 秒），超时后进程被强制结束。

## 崩溃了会怎样

插件进程意外退出时，Core 自动重启它。5 分钟内连续退出 3 次，Core 认为它有问题，停用它，并在日志和管理界面里报告。修好之后手动启用。

Handler 里的 panic 不会让进程退出：框架会接住它，记录错误，这一次调用失败，插件继续运行。

## 更新失败如何恢复

这是「代次」这个概念的用处。一个代次是一个组件的一份完整状态：程序、配置、数据库。

更新一个插件时：

1. Core 停止旧版本。
2. **把数据库复制一份**，新版本在副本上工作。
3. 启动新版本，走上面的启动顺序。新的建表步骤在副本上执行。
4. 成功：新代次生效，旧代次保留一段时间。
5. 失败：丢掉副本，重新启动旧版本，用原来的数据库。

修改配置也是同样的过程，所以填错配置导致启动失败时会自动退回原来的配置。

`alonabot rollback <ID>` 是手动退回上一个代次：程序、配置、数据库一起回到更新前的样子。更新之后产生的数据会丢失。

这个保护只覆盖框架管理的数据库。插件自己写的文件、外部的数据库，更新失败时不会被恢复。

开发时（`alonabot run` 运行的工程）没有这套机制：只有一个数据库文件，每次重启直接用它。

## 配置什么时候生效

插件运行期间，`p.Config()` 读到的配置不会变。机器人主人修改配置后，需要重新加载这个插件（界面上会提示），相当于用新配置启动一次。

[按会话设置](../advanced/profiles.md)的值是例外：修改后从下一条消息开始生效，不需要重新加载。

## 空闲时退出

开启[节省内存](../usage/settings.md#节省内存)后，一段时间没被用到的插件会正常停止。之后有消息、服务调用或 HTTP 请求需要它时，Core 重新启动它，再把请求交过去。

重新启动时用的是同一个代次：不复制数据库，不执行建表步骤，`OnStart` 和 `OnReady` 会再执行一次。所以这两个回调要能重复执行。

只有声明了支持的插件才会被这样处理。有后台协程、需要一直保持连接的插件不应该声明。
